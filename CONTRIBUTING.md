# Contributing to mfgparams

Thanks for considering a contribution. This file covers process — branching,
review, and this repo's spec-kit conventions. For getting a local environment
building and testing (required toolset, setup steps, and troubleshooting for
the issues contributors actually hit), see [`DEVELOPMENT.md`](DEVELOPMENT.md);
for the CI gate reference, see the README's
[Quality & Security Gates (CI)](README.md#quality--security-gates-ci) — this
document doesn't repeat either.

## Before you start

- Search open issues and PRs first; if none covers what you want to do, open
  an issue describing it before writing code, so the approach can be agreed
  on before you invest time.
- This project is governed by
  [`.specify/memory/constitution.md`](.specify/memory/constitution.md) — a
  numbered set of non-negotiable and negotiable principles (testing, i18n,
  CI gates, licensing, multi-agent tooling, manual verification for
  interactive features, etc.). Skim it once; PR review checks against it
  directly.

## Does this change need spec-kit?

This repo uses [Spec Kit](https://github.com/github/spec-kit) (`specs/NNN-*`,
`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`)
for **feature and behavior changes** — anything with `src/` code, tests, or a
CI gate for the spec/plan/tasks artifacts to bind to. Every shipped feature in
`specs/` went through this flow, and larger multi-PR features use a long-lived
integration branch per Constitution Principle XII rather than one oversized PR.

Skip spec-kit and open a **direct PR** instead for:

- Documentation-only changes (README, this file, code comments/docstrings).
- Edits to a hand-authored skill under `.github/skills/**` (see
  [`.github/skills/skill-authoring/SKILL.md`](.github/skills/skill-authoring/SKILL.md)
  for that specific checklist).
- Small, self-contained bug fixes with no design decision to record.

Spec-kit's value comes from diffing a spec against code that actually exists;
running the full ceremony on prose with no code behind it just adds artifact
drift with nothing to show for it. When in doubt, ask in the issue before
opening the PR.

**Do not hand-edit generated per-agent files** (`.github/agents/`,
`.github/prompts/`, most of `.claude/skills/`) — these are regenerated by
`specify integration upgrade` per Constitution Principle XI. A hand-authored
skill genuinely shared across agents lives once under `.github/skills/<name>/`
and is symlinked elsewhere, never copied.

## Making the change

- Follow [`.github/instructions/python.instructions.md`](.github/instructions/python.instructions.md)
  for Python style, typing, and testing conventions.
- New or changed calculation logic needs tests covering edge cases, and
  documented units/sources for any formula (Constitution Principle II/III).
- Any new user-facing string goes in the appropriate message catalog, never
  inlined at its call site — see README's
  ["Adding or changing a user-facing string"](README.md#adding-or-changing-a-user-facing-string)
  (Constitution Principle VIII).
- Changing or adding a console/TUI screen? Read
  [`.github/skills/tui-design/SKILL.md`](.github/skills/tui-design/SKILL.md)
  *before* implementing, and see Constitution Principle XIII: an
  interactive-UI feature's `tasks.md` needs a distinct, developer-performed
  manual-verification task — a green test suite is not sufficient evidence a
  rendering/interaction detail (color, layout, focus highlighting) is
  correct.
- If you must suppress a complexity (`ruff`/C901), security (`bandit`), type
  (`mypy`), or dependency (`pip-audit`) finding, use the tool's native
  suppression mechanism with an inline rationale comment. Complexity and
  security suppressions specifically also require the same rationale restated
  in the PR description's "Quality & Security Gate Exceptions" table (the PR
  template has this section pre-filled) — reviewers will reject a PR that's
  missing either half.

## Submitting the PR

- Open the PR against `main` (or the feature's integration branch, if one
  exists per Principle XII) using the repository's PR template.
- All required CI checks must pass: `ci-ok`, `Analyze (python)`, and CodeQL —
  see the README's CI table for what `ci-ok` aggregates and which jobs are
  path-based.
- At least one other contributor reviews the PR before merge (solo work is
  self-reviewed against the constitution checklist in
  [Development Workflow (Review Process)](.specify/memory/constitution.md#development-workflow-review-process)).
- Once merged, delete the branch — including any now-obsolete sub-branches of
  a completed integration branch.
